# OTP-first password recovery — 2026-10-16

## Approved behavior

The user requested email OTP verification before revealing the new-password and
confirmation fields at `/reset-password`. BR-AUTH-09 and the provider contract
now record the two-step clarification. Existing legacy reset links and combined
OTP API remain compatible.

## Implementation and security review

- `POST /auth/verify-reset-otp` validates email, challenge ID and six-digit code;
  service owns the transaction and locks. Successful verification consumes the
  OTP and creates a 256-bit random reset credential in the existing reset-token
  table, storing only its SHA-256 hash. Response is `Cache-Control: no-store`.
- Final password update reuses `/auth/reset-password`: password rules,
  single-use token validation, account state checks and session revocation.
  Verification alone never changes the password or revokes login sessions.
- Reset credential expires at the original OTP deadline. Resend invalidates
  existing credentials under the user lock; consumed/expired/replaced OTPs,
  purpose/email mismatch and five failed guesses remain rejected. Concurrent
  verification can issue only one credential. No OTP/token/password logging,
  schema change, new dependency, or account-enumeration response was added.
- Browser keeps the reset credential only in component memory. It mounts
  password fields after backend verification. A reload after verification
  requires requesting a new OTP. Existing countdown/resend component is reused.
  The API client excludes verification from session refresh/retry behavior.
- `ResetPasswordFields` is a real feature boundary for credential inputs;
  extracting it keeps the Page at 246 lines, below the 300-line review trigger.
  Service/controller remain within their existing responsibilities.
